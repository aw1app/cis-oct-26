SQL Injection, Simply Explained

A plain-language explanation of the issue in alert_utils.py.

The basic idea

This program looks up alerts that match a source name. It builds a database question by joining pieces of text together. The source name is supposed to be just a label, but the database may mistake specially crafted text for part of its instructions.

Imagine a librarian: You ask, “Find books with this title,” and give the librarian a title on a note. If the note is accidentally treated as a new command instead of just a title, the librarian might bring back books you did not ask for. That mix-up is the main idea behind SQL injection.

What could go wrong here?

If someone can control the source name sent to this function, they may be able to confuse the database's search. It could show alerts from more sources than intended or produce an error. The exact risk depends on how the program is connected to users and what data is in the database.

The Python SQLite execute() method rejects a request containing multiple separate SQL statements. That helps, but it does not stop specially crafted input from changing the meaning of the one statement being run.

How to prevent it

Use a placeholder for the source name. The database then receives the search instruction and the source value separately, so it knows the value is data, not a new instruction.

cursor.execute(
    "SELECT * FROM alerts WHERE source = ?",
    (source_name,),
)

In short: keep the database instructions separate from the values people provide.
